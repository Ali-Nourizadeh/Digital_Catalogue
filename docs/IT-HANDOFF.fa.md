# راهنمای استقرار کاتالوگ و محصولات به‌کوشان

## ساختار انتشار

کاتالوگ و محصولات در یک سایت استاتیک منتشر می‌شوند: کاتالوگ در `/` و محصولات در `/products/`. هر دو بخش از یک دامنه و یک ریشهٔ وب استفاده می‌کنند. به سرویس اپلیکیشن، Node.js، دیتابیس یا Docker نیازی نیست؛ استفاده از کانتینر فقط در صورت نیاز زیرساخت امکان‌پذیر است.

بستهٔ `release.zip` شامل سایت آمادهٔ اجرا و مستندات انتشار است؛ سورس توسعه، داده‌های ساخت و ابزارهای توسعه همراه آن نیستند. HTML، CSS و JavaScript موردنیاز مرورگر بخشی از سایت هستند و در وب قابل دریافت خواهند بود.

**ریشهٔ وب فقط `release/site/` است.** راهنماها، مجوز اصلی، manifest و هش‌ها خارج از ریشهٔ وب باقی می‌مانند. پوشهٔ `site/products/research/` استثنا نیست: فایل‌های بافت قابل دانلود در آن قرار دارند و برای عملکرد سایت لازم‌اند.

## پیش‌نیازهای محیط

- یک وب‌سرور استاتیک، مانند Nginx، Apache، Caddy یا IIS.
- دامنه یا زیردامنه و تعیین دسترسی عمومی یا داخلی.
- HTTPS با گواهی معتبر و برنامهٔ تمدید گواهی.
- مجوز خواندن فایل‌ها برای وب‌سرور؛ دسترسی نوشتن لازم نیست.
- تعیین مسئول نگهداری، نسخهٔ پشتیبان و روش به‌روزرسانی.

زیردامنهٔ اختصاصی، مانند `catalogue.company.ir`، ساده‌ترین گزینه است. برای انتشار در زیرمسیر، مانند `/catalogue/`، ریشه/alias، ریدایرکت اسلش و همهٔ لینک‌ها باید در همان آدرس واقعی آزمایش شوند.

## نصب ساده

1. صحت فایل ZIP با `release.zip.sha256` بررسی می‌شود.
2. ZIP در مسیر نصب استخراج می‌شود.
3. Document Root روی مسیر کامل `release/site/` و صفحهٔ پیش‌فرض روی `index.html` قرار می‌گیرد.
4. نام دامنه، HTTPS و MIME فایل‌های HTML، CSS، JavaScript، SVG، WebP و WOFF2 تنظیم می‌شوند.
5. مسیرها و عملکرد سایت پیش از انتشار نهایی آزمایش می‌شوند.

نمونه‌های `deploy/nginx.conf.example` و `deploy/Caddyfile.example` جایگزین هم هستند، نه دو سرویس موردنیاز. دامنه و مسیر فرضی آن‌ها باید تغییر کند. نمونهٔ Nginx روی پورت ۸۰ است و به‌تنهایی HTTPS فراهم نمی‌کند؛ TLS روی Nginx یا پراکسی موجود و هدایت HTTP به HTTPS لازم است. در شبکهٔ داخلی، گواهی سازمانی معتبر قابل استفاده است.

## نصب نسخه‌ای روی Linux/Nginx

نمونهٔ زیر به دسترسی مدیریتی نیاز دارد. `RELEASE_ID` باید با شناسهٔ واقعی نسخه جایگزین شود. مسیرهای نمونه قابل تغییرند.

```bash
sudo mkdir -p /var/www/behkooshan/releases/RELEASE_ID
sudo unzip release.zip -d /var/www/behkooshan/releases/RELEASE_ID
sudo find /var/www/behkooshan/releases/RELEASE_ID -type d -exec chmod 755 {} \;
sudo find /var/www/behkooshan/releases/RELEASE_ID -type f -exec chmod 644 {} \;
```

پس از تست نسخه و ثبت مقصد قبلی `current`:

```bash
sudo ln -s /var/www/behkooshan/releases/RELEASE_ID/release /var/www/behkooshan/current.next
sudo mv -Tf /var/www/behkooshan/current.next /var/www/behkooshan/current
```

این روش فرض می‌کند `current` وجود ندارد یا symlink است؛ نباید پوشهٔ واقعی باشد. `current.next` نیز نباید از اجرای قبلی باقی مانده باشد. ریشهٔ Nginx در این ساختار `/var/www/behkooshan/current/site` است. بعد از تطبیق تنظیمات دامنه، `nginx -t` و سپس reload انجام می‌شود. مجوز `777` لازم نیست و نباید داده شود.

در IIS نیز `site/` به‌عنوان سایت استاتیک، با default document برابر `index.html`، MIMEهای لازم و HTTPS تنظیم می‌شود.

## بررسی پس از نصب

- هشت مسیر اصلی README و لینک مستقیم یک محصول از هر زبان و نما پاسخ HTTP 200 دارند؛ مسیر ناموجود پاسخ 404 دارد.
- کاتالوگ و محصولات از طریق لینک‌های داخل سایت به یکدیگر متصل‌اند.
- بدون فیلتر هر چهار فهرست ۹۹ سنگ دارند؛ جست‌وجو و فیلتر نوع، مبدأ و رنگ درست کار می‌کنند.
- تصاویر، فونت‌ها، بزرگ‌نمایی، قبلی/بعدی و دانلود بافت بدون خطای بارگذاری اجرا می‌شوند.
- در موبایل، فلش برگشت فقط روی جزئیات محصول، بالای سمت چپ هدر دیده می‌شود. در ورود مستقیم، مقصد جایگزین فهرست همان زبان و نماست.
- گزینهٔ «فیلترها» بعد از عبور از بخش فیلتر در هر دو نما ظاهر می‌شود و به تنظیم فیلتر برمی‌گردد.
- فارسی و انگلیسی، دسکتاپ، موبایل عمودی و گوشی افقی بررسی می‌شوند.
- مستندات انتشار و فایل‌های توسعه از وب قابل دریافت نیستند؛ فایل‌های دانلود بافت در دسترس‌اند.

از داخل `release/`، بررسی سلامت همهٔ فایل‌ها در Linux:

```bash
sha256sum -c SHA256SUMS.txt
```

شناسهٔ کامیت، تعداد صفحات و هش فایل‌های سایت در `release-manifest.json` ثبت شده‌اند. سلامت بسته جایگزین تست تنظیمات سرور نیست.

## به‌روزرسانی و بازگشت

هر انتشار در پوشه‌ای جدا نگهداری می‌شود. پس از تست، `current` به نسخهٔ جدید اشاره می‌کند؛ بازگشت با اشارهٔ مجدد به نسخهٔ قبلی انجام می‌شود و مهاجرت دیتابیس وجود ندارد.

نام فایل‌های CSS و JavaScript هش‌دار نیست؛ cache یک‌ساله یا `immutable` مناسب نیست. نمونهٔ Nginx صفحات را بازاعتبارسنجی و فایل‌های استاتیک را یک ساعت cache می‌کند. در انتشار فوری، cache پراکسی یا CDN نیز باید تازه شود. شناسه و تاریخ هر نسخه برای نگهداری ثبت می‌شود.
