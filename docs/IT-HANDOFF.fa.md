# راهنمای تحویل و استقرار کاتالوگ به‌کوشان

## پیشنهاد اجرایی

این پروژه HTML/CSS/JavaScript استاتیک با فونت‌ها و تصاویر محلی است. پیشنهاد: یک زیردامنه اختصاصی مانند `catalogue.company-domain.ir` پشت HTTPS و وب‌سرور فعلی شرکت (Nginx، Apache، IIS یا Caddy). Node.js، Python، دیتابیس و سرویس اپلیکیشن برای اجرای سایت لازم نیستند. Docker برای این پروژه ضروری نیست؛ اگر استاندارد سازمان کانتینر است، IT می‌تواند همان فایل‌های استاتیک را در تصویر وب‌سرور مصوب خود قرار دهد.

آدرس نمونه است و دامنه واقعی باید از IT دریافت شود. فایل‌های تنظیمات این پوشه نمونه‌اند، نه تنظیم آماده سرور شرکت. هیچ دسترسی یا تغییری روی سرور شرکت انجام نشده است.

## محتویات تحویل

- ZIP انتشار: پوشه `site/` به همراه این راهنما، نمونه تنظیمات `deploy/`، مجوز و `release-manifest.json`.
- `source.zip`: سورس کامل، داده‌ها، قالب‌ها، ابزار ساخت و آرشیو مرجع؛ فقط برای نگهداری و توسعه، نه برای قرار دادن در document root.
- فایل SHA-256 برای هر ZIP؛ هش با فایل دریافت‌شده مقایسه شود.
- `release-manifest.json`: شناسه کامیت، وضعیت تغییرات محلی، تعداد صفحات، تعداد محصولات هر زبان/نما و هش فایل‌های سایت.

**فقط محتویات `site/` منتشر شود.** پوشه‌های داده، پژوهش، `.git`، ابزارهای ساخت و سورس نباید از وب قابل دانلود باشند. `products/research/` داخل `site/` عمداً باقی می‌ماند؛ فایل دانلود بافت محصولات از آن استفاده می‌کند.

## ایجاد دوباره بسته از سورس

روی دستگاه توسعه/CI، Node.js 24 و Python 3 نصب باشد. هیچ `npm install` برای ساخت لازم نیست:

```bash
node tools/build-catalogue.mjs
node tools/build-products.mjs
python3 tools/package-release.py --output ../catalogue-release-YYYYMMDD
```

مسیر خروجی باید تازه و خارج از ریپو باشد. اسکریپت در صورت لینک محلی خراب یا تعداد محصول غیر از ۹۹، تحویل را متوقف می‌کند. نسخه‌های HTML تولیدشده در سورس وجود دارند؛ IT برای انتشار ZIP نیازی به اجرای این دستورها ندارد. تغییر رسانه اصلی و تولید مجدد تصاویر فرایند جداگانه‌ای دارد؛ راهنمای README و ابزارهای derive مربوطه بررسی شوند.

## نصب پیشنهادی روی Linux/Nginx

IT دامنه، دسترسی شبکه (عمومی یا داخلی)، مسیر نصب و روش HTTPS را تعیین کند. نمونه زیر یک زیردامنه اختصاصی و نسخه‌های جداگانه را فرض می‌کند:

```bash
# فرمان‌های ادمین؛ فقط توسط IT و پس از جایگزینی نام نسخه و دامنه اجرا شود.
sudo mkdir -p /var/www/behkooshan/releases/RELEASE_ID
sudo unzip catalogue-release.zip -d /var/www/behkooshan/releases/RELEASE_ID
sudo find /var/www/behkooshan/releases/RELEASE_ID -type d -exec chmod 755 {} \;
sudo find /var/www/behkooshan/releases/RELEASE_ID -type f -exec chmod 644 {} \;
# قبل از تغییر current، نسخه قبلی را ثبت و نگه دارید.
sudo ln -s /var/www/behkooshan/releases/RELEASE_ID /var/www/behkooshan/current.next
sudo mv -Tf /var/www/behkooshan/current.next /var/www/behkooshan/current
```

برای این روش `current` باید وجود نداشته باشد یا symlink باشد، نه پوشه واقعی. اگر `current.next` از اجرای قبلی باقی مانده، اول علت را بررسی کنید. document root وب‌سرور دقیقاً `/var/www/behkooshan/current/site` باشد. نمونه `deploy/nginx.conf.example` را با دامنه واقعی و استاندارد شرکت تطبیق دهید؛ `nginx -t` سپس reload. فایل نمونه پورت ۸۰ دارد و به‌تنهایی HTTPS فراهم نمی‌کند؛ پیش از استفاده نهایی، TLS در Nginx یا reverse proxy شرکت فعال و HTTP به HTTPS هدایت شود. در شبکه داخلی از گواهی سازمانی مصوب استفاده شود؛ الزام امنیتی را غیرفعال نکنید.

وب‌سرور فقط مجوز خواندن نیاز دارد؛ به فایل‌ها مجوز نوشتن یا `777` ندهید. MIME صحیح HTML، JavaScript، CSS، SVG، WebP و WOFF2 برقرار باشد. در Windows/IIS همین `site/` به‌عنوان سایت استاتیک با default document برابر `index.html`، MIMEها و TLS تنظیم شود.

برای انتشار زیرمسیر، مثلاً `/catalogue/`، در تست حتماً همان مسیر واقعی بررسی شود؛ لینک‌های خود سایت نسبی‌اند اما document root/alias و ریدایرکت اسلش باید درست تنظیم شوند. زیردامنه اختصاصی روش ساده‌تر و کم‌ریسک‌تر است.

## مسیرها

- `/` و `/en/`: کاتالوگ فارسی و انگلیسی.
- `/wide/` و `/wide/en/`: کاتالوگ افقی.
- `/products/` و `/products/en/`: فهرست محصولات.
- `/products/wide/` و `/products/wide/en/`: فهرست افقی.
- صفحات جزئیات زیر مسیر `product/` هر کدام از چهار نسخه محصولات؛ از لینک همان فهرست استفاده کنید.

## پذیرش پیش از تحویل نهایی

1. هش ZIP را بررسی کنید؛ از محتوای `site/` نسخه staging بسازید، نه از کل ریپو.
2. هر هشت مسیر بالا و لینک مستقیم یک محصول از هر زبان/نما HTTP 200 بدهد؛ مسیر ساختگی 404 بدهد.
3. جست‌وجو، فیلتر نوع/مبدأ/رنگ، پاک‌کردن فیلتر و بازشدن لینک فیلترشده در تب تازه درست باشد. بدون فیلتر هر چهار فهرست ۹۹ سنگ دارند.
4. فونت، لوگو، تصاویر، بزرگ‌نمایی، قبلی/بعدی و دانلود بافت بدون 404 یا خطای کنسول باشد.
5. در موبایل فلش برگشت فقط در صفحات جزئیات، بالای گوشه چپ هدر نمایش داده شود؛ نه در هیچ نسخه زبانی/افقی/عمودی از دو صفحه اصلی کاتالوگ و محصولات. کلیک معمولی به صفحه قبلی تاریخچه برگردد؛ اگر تاریخچه برگشت وجود ندارد، به فهرست محصولات همان زبان/نما برود. دکمه‌های عمومیِ برگشت پایین صفحه و کنترل همبرگری قبلی حذف شده‌اند؛ گزینه اختصاصی «فیلترها» در فهرست محصولات، پس از عبور از بخش فیلتر، نمایش داده می‌شود و در هر دو نمای عمودی و افقی به بخش تنظیم فیلتر برمی‌گردد.
6. فارسی/انگلیسی، عمودی/افقی، موبایل ۳۹۰px و حالت گوشی افقی ۸۴۴×۳۹۰ بررسی شود. دکمه شناور در نمایشگر تصویر دیده نشود.
7. HTTPS، تمدید گواهی، پشتیبان، دسترسی شبکه و مالک نگهداری تأیید شود. لینک‌ها و تصاویر خارجی را در شبکه واقعی شرکت نیز بررسی کنید.
8. فایل‌های منبع/آرشیو خارج از document root باشند. فونت‌ها و تصاویر برای انتشار شرکتی از نظر مجوز استفاده توسط مالک پروژه تأیید شوند. **مانع انتشار عمومی:** طبق docs/DESIGN.md، فونت لاتین TT Firs Neue موجود نسخه Trial است؛ پیش از انتشار روی دامنه شرکت باید مجوز وب تجاری تهیه و فایل‌های فونت مجاز جایگزین شوند. صرف آماده‌بودن فنی ZIP به معنی مجاز بودن انتشار تجاری فونت نیست.

## به‌روزرسانی و بازگشت

هر انتشار پوشه نسخه جداگانه داشته باشد. `current` پس از تست به نسخه جدید اشاره کند. برای rollback همین symlink را به نسخه قبلی برگردانید؛ به دیتابیس یا مهاجرت داده نیاز نیست. فایل‌های CSS/JS نام هش‌دار ندارند: از cache یک‌ساله/immutable استفاده نکنید؛ نمونه Nginx HTML را revalidate و asset را یک ساعت cache می‌کند. در انتشار فوری cache پراکسی/CDN شرکت هم پاک شود. شماره نسخه/کامیت و تاریخ تحویل ثبت شود.

## وضعیت GitHub Pages

`main` منبع اصلی است، اما طبق تنظیم فعلی مخزن، workflow انتشار Pages هنوز از `Behkooshan-catalogue` اجرا می‌شود. ZIP شرکتی مستقل از GitHub Pages است. انتقال workflow به main نیازمند دسترسی جداگانه workflows است؛ شاخه‌های انتشار قدیمی را بدون انتقال و تست حذف نکنید.

## اطلاعاتی که IT باید نهایی کند

دامنه/زیردامنه، Linux یا Windows، وب‌سرور، شبکه عمومی یا داخلی، HTTPS و reverse proxy، مسیر نصب، مالک به‌روزرسانی و روش backup. ارسال رمز سرور داخل چت لازم نیست؛ این بسته برای تحویل بدون دسترسی سرور طراحی شده است.
